----Points d'attention (Anticipation technique)
Risque de "God Object" sur Demande :
L'entité Demande centralise énormément de relations (Dossier, Contrat, Local, Historique, VoteCommission, AppelCandidature).
Recommandation : Au niveau de l'implémentation Django, veille à ne pas surcharger les méthodes du modèle Demande. Utilise le pattern Service Layer (ex: DemandeService.valider_demande()) pour isoler la logique métier complexe et garder le modèle léger.
Gestion des Paiements asynchrones (MOBILE_MONEY) :
Le diagramme intègre Paiement avec le mode MOBILE_MONEY. Les paiements par API mobile money nécessitent souvent de gérer des callbacks (webhooks) asynchrones.
Recommandation : Il faudra probablement, en implémentation, une table supplémentaire (ex: TransactionLog) pour stocker le payload brut des fournisseurs de paiement (Statut de l'API, Provider ID, erreurs) afin de faciliter le débuggage en cas d'échec de transaction.
Redondance des coordonnées GPS :
Plainte et InspectionQHse ont toutes deux les attributs latitude et longitude en Float.
Recommandation : Si le système doit faire des requêtes spatiales (ex: "Trouver toutes les plaintes dans un rayon de 1km"), il vaudrait mieux utiliser GeoDjango avec PostGIS (PointField). Si c'est juste pour affichage sur une carte frontend, les Float suffiront.
